# Experimental Independence Controls

MORSE uses methodological inheritance without evidence inheritance.

## Independence rule

A result generated by another project may motivate a MORSE hypothesis, inform an apparatus design choice, or provide a comparison target. It is not counted as MORSE evidence unless the result is reproduced by the MORSE protocol and recorded in MORSE evidence artifacts.

## Independence dimensions

### Implementation independence

MORSE scheduler, topology, gates, and hub semantics are maintained in this repository. Shared utility code is permitted only when its behavior is version-pinned and its role is documented.

### Configuration independence

MORSE experimental configurations are version-controlled and hashed. Changes to topology, ratio definitions, task sets, or endpoints create a new configuration identity.

### Execution independence

Each condition receives independently derived deterministic seeds. Paired comparisons reuse the same task/seed identity across conditions where appropriate, but never reuse mutable state between conditions.

### Analysis independence

The analysis specification is frozen before confirmatory unblinding. Exploratory analyses must be labeled exploratory and must not redefine the primary endpoint retroactively.

### Evidence independence

MORSE artifacts carry commit/configuration identifiers and content hashes. External project artifacts can be cited as provenance or prior work but are not silently incorporated into MORSE result counts.

## Shared-method risk

A shared validator or shared execution component can create correlated failure modes. Where independence is claimed, MORSE should prefer independently implemented checks for critical predicates or explicitly disclose shared dependencies.

## DGAF/PDMAL relationship

DGAF/PDMAL research is a methodological and architectural source of prior experience only. MORSE remains a separate project with separate hypotheses, protocol, artifacts, and empirical claims.
